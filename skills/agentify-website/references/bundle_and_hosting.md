# Bundle files, mounting and hosting

## Output layout

The agentified site is a copy of the original site with these additions:

```text
<out>/
  index.html                  existing page + assistant section (templates/assistant-section.html)
  styles.css                  existing styles + templates/assistant.css
  <page script>               existing page script (one or more modules), now exporting the page object (App.page)
  site.js                     boots the assistant (templates/site.js)
  site-actions.js             registers site actions (templates/site-actions.js)
  <network>.hocon             source of truth for the network (templates/network.hocon)
  <network>.network.json      generated by scripts/build_network.mjs; do not edit by hand
  agent-manifest.json         templates/agent-manifest.json
  links.json                  templates/links.json
  agent-mcp.json              generated from the manifest; do not edit by hand
  .well-known/                generated discovery files (see "How others find the site")
  runtime/                    copied unchanged from the skill's runtime/
  tests/                      templates/tests/, filled in for this site
```

## The runtime

Copy the skill's `runtime/` folder without changes. `runtime/README.md` lists how it
differs from nsdeploy's runtime. If a site needs a runtime change, report it instead of
editing the copy.

## The manifest

`agent-manifest.json` sits next to the network file. The runtime reads:

| Field | Purpose |
| --- | --- |
| `networks[0].name`, `.front_man`, `.hocon` | Network name (the `.hocon` file name without extension), front agent, and `./<network>.network.json`. |
| `networks[0].description` | The first line of the chat's opening message, shown until the visitor adds a key (`runtime/ui.js`). Write it as one sentence a visitor reads. Once a key is set, `site.js` shows `GREETING` instead. |
| `networks[0].sample_queries` | Public metadata for people and other sites. The runtime UI does not show them. |
| `brand` | The name in the chat header. |
| `theme.primary` | Set inline as `--ns-primary` on the mount, so it overrides the CSS value. |
| `llm_router.base_url`, `.byok_router`, `.mock` | Default router for BYOK. `mock: false` for a real site. |
| `peer_policy` | `"mode": "closed"` unless the network calls other sites. |
| `deployment.mode` | Must be `"static"`. |
| `actions.version`, `.module`, `.agentTools` | `1`, the actions module path, and the action names that become `website_*` tools. |
| `linking.exports[].aliases` | Names that match when another site links to this one by a name instead of the exact URL. |

The manifest also has `linking.protocol` (`<protocol_name>-link/v1`) and `agent_mcp`
(`<protocol_name>-agent-mcp/v1`, and `available: false` because a static site has no MCP
server). The runtime does not read these. `build_network.mjs` copies `linking` and
`agent_mcp` into the discovery files. The protocol name is in `runtime/README.md`.

In `linking.exports[0].aliases`, list the network name and the front agent name; if they
are the same, list it once.

## Mounting

`site.js` calls `boot("#agent-app", {originUrl, sandboxWorkerUrl})`. `originUrl` is the
folder that holds `agent-manifest.json`. The runtime resolves the network, `links.json` and
the actions module against it, so the assistant also works under a subpath. The mount
element needs `data-ns-slot="header"`, `"chat"`, `"agents"` and `"settings"` children.
The settings slot keeps the BYOK settings out of the chat box. Without it, the open
settings sit inside the chat box and leave little room for the messages. Style the mount
through the `--ns-*` variables in `templates/assistant.css`.

On a site with several pages, mount the assistant on one page only: the page whose script
the actions wrap. The actions module imports that script, which needs that page's
elements. On the other pages, link to the assistant section instead, such as
`index.html#assistant`.

Keep the page usable when boot fails. `site.js` says so in `#assistant-status`, logs the
error to the console and leaves the page alone.

The site's global styles for `button`, `input`, `label`, `select`, `legend` and headings
also apply to the assistant. `templates/assistant.css` undoes the common ones, but open
the page in a browser and check the chat, a form and a choice list in the chat, the
settings panel and the confirmation dialog. Hover the assistant's buttons too, such as
**Developer**: a site's `button:hover` rule reaches them. Add overrides under `#agent-app`
for the chat and the settings panel. `site.js` adds its confirmation dialog to `<body>`,
outside `#agent-app`, so style it with `.assistant-review` rules. The runtime's own
dialog, for actions `site.js` does not list, takes the `body > dialog` rules. If the site
has its own dialogs under `<body>`, check that these rules do not change them.

## Check without a key

A form, a choice list or the dialog appears only after a model reply, which needs a key.
To check them without one, run this in the browser's DevTools console on the page with
the assistant. Replace the two `<...>` with an irreversible action and valid arguments
for it.

```js
const { renderPresentation } = await import("./runtime/ui.js");
renderPresentation(document.querySelector("#ns-msgs"), {
  version: 1,
  components: [
    {
      kind: "form",
      title: "Style check",
      schema: {
        properties: {
          name: {type: "string"},
          size: {enum: ["Small", "Large"]},
          time: {
            enum: ["Lunch", "Dinner"],
            "x-ui": {widget: "radio"},
          },
          extra: {type: "boolean"},
        },
      },
    },
    {
      kind: "choice",
      title: "Choice check",
      options: [
        {
          title: "First choice",
          subtitle: "Its subtitle",
          meta: "$1.00",
        },
      ],
    },
  ],
}, null);
void window.__nsweb.engine.onActionConfirm([
  {
    action: "<irreversible_action>",
    description: "",
    origin: location.origin,
    effect: "irreversible",
    arguments: {<valid arguments>},
  },
]).then(console.log);
```

The first call adds a form and a choice list to the chat. The form has a text field, a
drop-down list, radio buttons and a checkbox. Check that the choice shows its title,
subtitle and price on three readable lines. The second call opens the dialog with the
words and details from `site.js`. Nothing runs and nothing is sent: the form's button and
the choice do nothing, and the confirm button only closes the dialog. Press the decline
button, and the console logs `false`. With arguments the site would refuse, no dialog
opens, and the console shows the site's reason as an error. To run the snippet from a
script, send it to the DevTools protocol's `Runtime.evaluate` with `replMode: true`, which
allows the top-level `await`. The call returns before the dialog closes. Reload the page
to remove the form and the choice list.

To see what a read action returns, such as one that needs `DOMParser`, run this. Replace
`<read_action>` with its name and `{}` with its arguments. `execute` asks its second
argument to approve the call. `Boolean` approves anything at once, so the snippet checks
`entry.effect === "read"` and never runs a write or irreversible action. Check the
content, such as each fee row and each link's `href`.

```js
const { engine } = window.__nsweb;
const scope = {
  base: engine.top.base,
  network: engine.top.network.name,
};
for (const entry of engine.actions.catalog(scope)) {
  if (entry.name === "<read_action>" && entry.effect === "read") {
    const plan = engine.actions.prepare({
      kind: "action",
      action: entry.ref,
      arguments: {},
    });
    console.log(JSON.stringify(await engine.actions.execute(plan, Boolean, "console-check"), null, 2));
  }
}
```

## Serving and trying it

ES modules and `fetch` need HTTP, not `file://`. Bind to `127.0.0.1`, so the site is not
reachable from the local network during the check:

```shell
python3 -m http.server 8080 --bind 127.0.0.1 --directory <out>
```

On Windows, use `python` instead of `python3`.

Open http://127.0.0.1:8080/, expand **BYOK / router settings**, and enter an API key,
model and router base URL. Then select **Apply, save & reload**. If you served another
folder on the same port before, the browser may still show its cached files, with no
assistant. Use another port, or reload while holding Shift.

On `localhost` and `127.0.0.1`, the runtime also copies saved setups, keys included,
into a cookie for 180 days, so the settings follow you across local ports
(`runtime/byok.js`). Any page served from that host, on any port, can read it. For a
local check, use a key with a low spending limit. Afterwards, delete the saved setup in
the settings and close the tab. A hosted site on any other domain keeps the key in that
site's own browser storage only.

## Providers and other things to warn about

- The browser calls the LLM router directly, so the router must allow CORS. OpenAI,
  OpenRouter and LiteLLM work. Anthropic's API and hosted Otari do not. See the
  [LLM provider notes](https://github.com/cognizant-ai-labs/agentic-web/blob/main/docs/providers/providers.md).
- Pick a model that reliably makes tool calls. Without tool calls the agent cannot read
  the page or act on it.
- If the router publishes `/models` and the model is not listed, the chat refuses it
  ("Model X is not published by this upstream").
- `http://localhost:8080` and `http://127.0.0.1:8080` are different origins with separate
  saved settings.
- Chrome logs a verbose "[DOM] Password field is not contained in a form" message for
  the API key field. It is harmless.
- After a visitor applies a key or model with a router other than `llm_router.base_url`,
  each page load logs an error for `<router origin>/agent-manifest.json`. It is harmless.
- Everything in the network file, including instructions, is public.

## Static hosting

Any static host works. So that other sites and tools can read the public files, serve
these with `Access-Control-Allow-Origin: *`: `agent-manifest.json`,
`<network>.network.json`, `links.json`, `agent-mcp.json` and the two `.well-known` files.
Do not add that header to business endpoints. Serve `runtime/sandbox-worker.js` with the
`Content-Security-Policy` below. If the site is under a subpath, add it to each path.

On Netlify and compatible hosts, put this in a `_headers` file at the site root:

```text
/agent-manifest.json
  Access-Control-Allow-Origin: *
/<network>.network.json
  Access-Control-Allow-Origin: *
/links.json
  Access-Control-Allow-Origin: *
/agent-mcp.json
  Access-Control-Allow-Origin: *
/.well-known/<protocol_name>.json
  Access-Control-Allow-Origin: *
/.well-known/<protocol_name>-agent.json
  Access-Control-Allow-Origin: *
/runtime/sandbox-worker.js
  Content-Security-Policy: default-src 'none'; script-src blob:; connect-src 'none'; worker-src 'none'
```

On Apache, put this in `.htaccess`:

```apache
<IfModule mod_headers.c>
  <FilesMatch "^(agent-manifest\.json|<network>\.network\.json|links\.json|agent-mcp\.json|<protocol_name>\.json|<protocol_name>-agent\.json)$">
    Header always set Access-Control-Allow-Origin "*"
  </FilesMatch>
  <Files "sandbox-worker.js">
    Header always set Content-Security-Policy "default-src 'none'; script-src blob:; connect-src 'none'; worker-src 'none'"
  </Files>
</IfModule>
```

Use HTTPS in production: the visitor's key is stored in the browser for this origin.

## How others find the site

The spec needs no central registry. People find the site through lists and registries,
such as the [NANDA Index](https://nandaindex.org/) and the
[list of agentic websites](https://github.com/cognizant-ai-labs/agentic-web/blob/main/docs/agentic_websites.md),
which takes pull requests. Both publish the site, so leave them to the user or ask first.

Other agent sites cannot call a network built with this skill yet. A caller first loads
the site's actions from a page that this skill does not publish. After about 10 seconds,
the caller's page asks its own visitor to open that page in a popup, which cannot connect
either. The skill also does not set up calls from this network to other agent sites.

- **Network URL.** The network's address is the folder that holds `agent-manifest.json`,
  then the network name, for example `https://pizza.example/little_oven_assistant` (spec
  section 3.2). Registries may ask for it.
- **Discovery files.** `build_network.mjs` writes `.well-known/<protocol_name>.json` (a
  copy of the manifest's `linking`), and `.well-known/<protocol_name>-agent.json` and
  `agent-mcp.json` (copies of `agent_mcp`). The spec calls them optional (section 3.3),
  and the browser runtime does not read them. nsdeploy's linker reads the first one and
  falls back to `agent-manifest.json` when it is missing. The spec puts discovery
  metadata under `.well-known/nsdeploy/`. nsdeploy writes the two `.well-known` files
  above instead, so keep their names. Tools look for `.well-known/` at the domain root,
  so these files help only when the site is at the root.
- **A2A Agent Card.** A site may also publish `/.well-known/agent-card.json` for A2A
  clients (spec section 3.3). The runtime does not read it, and this skill does not
  create one.
